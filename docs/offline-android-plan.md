# Android offline work (in progress)

The current APK remains an online WebView. Do not describe it as offline-ready. The user chose to keep the latest six messages from **all chats**, plus available attachments, offline (including chats not previously opened) and to use Android's device lock for offline access. Loading older messages requires connectivity. Calls, receiving messages, online presence, first sign-in, cloud AI and sync still require connectivity. Sending and changing settings must be blocked while offline, not silently queued.

`OfflineVault` is an **unwired storage primitive**, not an offline implementation. It uses an Android Keystore AES-GCM key requiring recent device authentication, account/item-bound authenticated data, private no-backup storage, atomic writes and per-item size limits. The implementation still needs device tests, explicit screen-lock enrollment and credential prompts. It has not been security-reviewed. The 60-second keystore authentication window is not itself an app session lock: a separate native UI gate must protect each offline launch and resume, including task previews. A device with no secure screen lock must not expose offline data. If the device lock or keystore key is reset, the cached copy may become inaccessible; re-download after connecting.

Before shipping an offline APK:
- Build an offline reader bundled with the APK, so a cold start does not depend on network or cached hosted HTML. Explicitly label stale data and unavailable features.
- Add an explicit Android device-credential prompt and resume gate, handling cancellation, no secure lock, lifecycle/recreation and lock changes; avoid WebView JS interfaces exposed to arbitrary frames. Never bypass the existing online app-password gate based on a web-controlled flag.
- Prefetch the latest six messages for every accessible chat (including unopened chats) and available attachments, scoped to the authenticated account. Use an RLS-protected, paginated/bounded sync, stage each complete snapshot atomically, cap storage, and label partial or unavailable attachments honestly. Obtain current account identity safely; do not cache auth tokens or whole sensitive server responses indiscriminately.
- Clear account data on sign-out or account switch, handle remote revocation honestly (it cannot be checked while offline), deletion and edits on reconnect, app uninstall, cache eviction, and corrupted or invalidated keys. Avoid background copying after sign-out and prevent other accounts reading snapshots.
- The user chose **save and sync later** for offline edits, deletions and reactions, with an explicit pending state until the server confirms each change. Sending messages and changing settings must remain blocked offline, with no automatic message outbox. Design the encrypted per-account mutation queue to survive restarts, handle duplicate attempts, conflicts, failures, sign-out and account switches, and never show an unconfirmed remote change as complete. Reconcile with the server on reconnect; specify safe behavior for other shared actions such as read receipts and uploads.
- Test airplane-mode cold start and resume, no/changed screen lock, failed auth, sign-out/account switch, local data removal, media, quota, corrupt data and reconnect on multiple real Android versions. Test security boundaries and cryptography with Android instrumentation, not only source-text checks. Build and publish a new APK only after this works; the previous CI debug key is different and an upgrade may require uninstalling, erasing local data.

## Snapshot groundwork (not connected)

`lib/offline/snapshot.ts` builds the latest six messages from every enumerated chat, stages available attachments via an abstract transaction, removes online attachment URLs from the snapshot, and aborts replacement on account changes, cancellation, missing pages or storage errors. Unavailable attachments are labeled rather than silently presented as saved. `lib/offline/supabase-source.ts` provides a keyset-paginated, RLS-scoped source, strict reaction and quote reads, origin/path-restricted bounded media downloads, and non-destructive temporary-video access. These modules have unit tests but are **not wired to the app** and do not provide persistent storage, device authentication, offline reading or a mutation queue. The future native sink must enforce the documented atomic session-generation check, encrypted staging, quotas and cleanup. Native storage currently has a 16 MB item limit, so larger attachments need authenticated chunked storage; the source's 50 MB cap is not proof they can yet be saved. The paged scan is not a database transaction and needs reconciliation for membership changes during sync. Do not publish a new APK as offline-ready on this basis.

## Mutation replay groundwork (not connected)

`lib/offline/mutation-queue.ts` defines an account- and generation-scoped queue protocol for edits, deletions and reaction changes. It rejects new message sends, keeps lost-response operations pending with the same id, stops on conflict, and requires an atomic local snapshot update before removing a server-confirmed operation. Unit tests exercise cancellation, stale accounts, duplicate ids, CAS contention, lost replies and corrupted state. **No encrypted queue store, conflict-resolution UI, server idempotency/conditional-write RPC, or integration exists yet.** Unsent repeated edits or reactions can be coalesced safely, while changes to the same lane during an in-flight or conflicted operation are rejected instead of silently lost; receipt-linked chaining and conflict-resolution UX are still needed. The existing online edit/delete/reaction endpoints are not safe replay adapters because they do not provide the required atomic idempotency receipts or revision checks.

## Interim safety (not offline functionality)

When the browser explicitly reports offline, remote sends and retries are refused rather than queued, with the text draft kept in the composer. Edits, deletions and reactions are refused with a clear message; they are **not** saved for later yet. Remote reactions are no longer displayed as successful before the server confirms the operation, and an ambiguous failed response is reported instead of silently treated as saved. Android-shell settings changes are blocked on a known offline connection; sign-out, immediate locking and disabling automatic analysis remain available for safety. `navigator.onLine` is only a negative hint, not proof of backend reachability or delivery. These guards do not provide an offline reader, queue, encryption, or sync.

`lib/offline/pending-view.ts` is a pure, tested view projection for the future reader: pending/in-flight/conflicted operations are visibly marked, pending deletion remains visible, and operations outside the latest-six window remain available as detached pending items. It performs no writes and is not connected to the app. Missing media is marked unavailable and remote avatar URLs are stripped from snapshot data; this does not implement attachment storage.
