# Web Push setup (required before notifications work)

Push is opt-in per device. It works for live Supabase accounts over HTTPS on browsers that support Web Push; on iPhone/iPad, iOS/iPadOS 16.4+ requires installing Dolemon to the Home Screen and enabling notifications from that installed app. Browser/OS permissions, battery policies, network and push provider availability still affect delivery. Demo mode has no server delivery. Only a generic “You have a new message” notification is sent, without the sender or message text. This is not an end-to-end encrypted messaging system.

## Deployment

1. Back up and verify your Supabase schema in staging. Apply `docs/migrations/012_push_notifications.sql` after the earlier migrations. Check RLS with two separate test accounts: each must see and modify only their own subscriptions, and neither can access `push_notification_events`.
2. Generate a unique VAPID keypair privately, e.g. `npx web-push generate-vapid-keys`. Add `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (public), `VAPID_PRIVATE_KEY` (secret), and `VAPID_SUBJECT` (e.g. a `mailto:` contact) to the deployment environment. Never paste the private key in chat or source control. **Keep the same keypair between deploys**: rotating it invalidates existing subscriptions and users must opt in again.
3. Add `SUPABASE_SERVICE_ROLE_KEY` (secret, server only) and a strong, random `PUSH_WEBHOOK_SECRET` (at least 32 characters, secret, server only). Never expose the service role key through `NEXT_PUBLIC_` variables. Deploy/rebuild after adding environment variables.
4. In Supabase Database Webhooks, create an **INSERT** webhook on `public.messages`, POST to `https://YOUR_APP_DOMAIN/api/push/message` and set header `x-dolemon-webhook-secret` to the exact secret. Do not put the secret in the URL. Use a preview-specific URL, project and secrets when testing. The endpoint validates the event, rereads the message and membership from the database, excludes the sender, and atomically deduplicates webhook retries by message ID.
5. On two separate accounts/devices, enable **Settings → Notifications**, allow phone/browser permission, close the recipient app, and send a message. Verify the generic notification arrives and opens the correct chat. Test both iOS Home Screen and Android separately. Disable it and sign out to verify the device unsubscribes. Remove expired endpoints and check server/webhook delivery logs without logging subscription URLs or keys.

A successful subscription alone does **not** prove the database webhook was installed or that notifications will arrive. Check delivery end to end. Push is best effort: the provider, webhook, device, or network can fail; deduplication avoids duplicate sends but transient errors after a claim are not retried. The existing per-conversation mute setting is device-local and does not currently suppress server push. Sign-out attempts to unsubscribe the current device, but network failures can leave a stale server row until it expires. No cross-device notification preferences or delivery receipts are provided.
