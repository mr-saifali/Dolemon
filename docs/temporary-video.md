# Temporary video handoff

Videos are stored in the sending browser's IndexedDB, then uploaded **directly to a private Supabase Storage bucket** (not through the Next.js server). MP4, WebM and MOV up to 50 MB are accepted; playback depends on each device's supported codecs. The recipient can save the video to their device while the temporary copy remains available. The app tries to delete the server object only after the recipient's IndexedDB transaction commits. If the deletion succeeds, other devices cannot download that copy; ask the sender to resend. If deletion fails, cleanup removes it later. Browsers can evict local data or lose it when site data is cleared; local copies are per-account on that browser, not a synced gallery or encrypted vault. Saving to Files uses the device's normal download flow.

Each server copy becomes **inaccessible to users after seven days**, even if cleanup is delayed. Actual deletion requires the scheduled cleanup below. Deleting a message or chat attempts to remove its local copies on the current device, but does not immediately erase uploaded video objects or other users' local copies; the cleanup job deletes expired server objects. As with existing attachments, this is not end-to-end encryption. Uploading the file still uses Supabase bandwidth and temporary storage, and standard uploads do not resume after interruption. The sender must stay in the chat while it uploads. Existing photo, voice and file attachments continue to use the legacy public bucket.

## Deployment requirements

1. Back up and apply `docs/migrations/013_temporary_video.sql` in staging after the base messaging/media schema. It creates a separate **private** bucket and member-scoped RLS. Confirm Supabase project upload limits permit 50 MB, and test policies with sender, recipient and unrelated signed-in account. Do not alter the legacy public `chat-media` bucket.
2. Configure the server-only `SUPABASE_SERVICE_ROLE_KEY` and a strong, random `CRON_SECRET` (at least 32 characters). Never put either in `NEXT_PUBLIC_` variables or share them in chat. `vercel.json` schedules `/api/video/cleanup` daily; Vercel must send the secret as `Authorization: Bearer <CRON_SECRET>`. Deploy after configuration. For non-Vercel hosting, use a scheduler to call that authenticated endpoint daily.
3. Confirm the cron job is actually running and monitoring errors/backlog. It removes up to 500 expired objects per run via the Storage API, then removes their metadata. Expired-but-not-yet-cleaned objects can still consume storage. If the cron isn't configured or fails, they remain on the server despite being inaccessible to app users. Never delete `storage.objects` rows directly with SQL.
4. Test a real two-account flow on separate devices: upload, recipient save/play, sender remains playable, recipient download failure does not delete the object, first-recipient cleanup, expiry, logout/account switch, local quota/full storage, interruption, deletion and scheduled cleanup. Verify access fails for unrelated accounts. No live device or production RLS verification has been performed by the development sandbox.
